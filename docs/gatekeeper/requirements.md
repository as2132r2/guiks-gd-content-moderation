## 十二、轨道 C 详解：冲突与分层

开工前把这一节读完。账号系统是**唯一一个会碰到所有其他轨道**的改动，冲突不是假想的。

### 八个冲突，都有解法

| # | 冲突 | 为什么是真冲突 | 解法 |
| --- | --- | --- | --- |
| **①** | **演示的「一屏切三个角色」vs 登录** | 演示脚本 1:55 是「编辑 → 主任 → 分管领导，切换器一屏演完」。加真登录后切角色 = 登出再登入，**演示当场断裂** | **一个账号持有多个角色**。演示账号持全部三个流程角色，切换器保留，语义从「切换是谁」变成「切换以什么身份行使」。演示不变，机制变真——而且这正是 business-process §二 要求的「角色可合并」 |
| **②** | §八 与 plan §十三 白纸黑字写了「⛔ 用户与权限体系」 | 作品说明要照着讲，口径不能自相矛盾 | 边界收窄而不是取消：**不做的是「权限配置界面」**，角色↔权限是代码内固定组合。两处文档已同步改口径 |
| **③** | **轨道 A 与 C 同改 transition handler** | A 改状态机迁移逻辑，C 改 `role` 的来源，是同一个函数 | **接口约定先于实现**：C 先落中间件，把已校验的 role 注入 context；A 的 handler 只从 `c.get('role')` 取，不关心它哪来的。约定定下来两边就能并行 |
| **④** | **16 个 API 测试会全挂** | `workbench-api` 12 例 + `manuscripts-api` 4 例都直接 POST `role`，加鉴权后全部 401 | 夹具与修复**必须在同一个 PR**（7.24）。不许「先加鉴权，测试下个 PR 修」——那样 `main` 会红着过夜 |
| **⑤** | **台领导不能进状态机** | 若把 `station-leader` 直接塞进 `workflowRoles`，`nextActions()` 会给它算按钮、`waitingOn()` 可能返回它，**状态机被污染** | 类型分层：`WorkflowRole`（三个，进流程）⊂ `SystemRole`（四个）。状态机只认前者（7.18） |
| **⑥** | **C 与 B 同改 `workbench-view.ts`** | C 改顶栏（用户名 / 登出 / 角色显示），B 重做 `reviewPanel`，同一个文件 | 顶栏与 panel 是不同函数。登录页**单开 view 文件**，不要塞进 `workbench-view.ts` |
| **⑦** | **`actorNames` 固定假人被替换** | 现在留痕里的「编辑·张敏」来自代码常量，换成真人后来源变了 | 种子账号的 `display_name` **必须沿用这三个名字**（7.13），否则演示截图与既有留痕对不上 |
| **⑧** | **`contracts.ts` 被两条轨道同时改** | A 的 5.9 校次契约、C 的 7.18 角色分层，都动共享契约 | **串行，不并行**。且按 CLAUDE.md 硬约束 2，改它需另一人复核——这条不因赶工取消 |
