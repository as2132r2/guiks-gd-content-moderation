# 业务流程设计

> 把关人的稿件生命周期、角色、状态机与留痕规则。
> 设计约束来自 [市场格局](market-landscape.md) 第五节的中小型融媒体中心真实条件，不是拍脑袋。

## 一、三条设计原则

### 1. 一条路走到黑，没有分支

不做功能菜单，只有一条链路。用户在任何时刻**只有一个「下一步」**。

**为什么**：中小型融媒体中心「采编人员对新设备和新系统掌握不全面、使用不熟练」，技术支撑力量不足。
功能越多，弃用越快——这就是「建而不用」的机制。**我们对大洋的优势不是功能多，是它那套在人手紧的编辑部跑不起来。**

### 2. 预检只标注，不阻断（硬拦那一档除外）

人少，阻断就是卡死，卡死就是弃用。预检的产出是**标注**，不是**闸门**——
除了入口那一层的硬拦（明确违法且与新闻业务无关），其余一律标出来让人决定。

### 3. 每一次流转都留痕，且留痕本身要有管理价值

不能只为合规留痕，那样没人维护。留痕必须能回答台领导关心的问题。见第四节。

## 二、角色

| 角色 | 对应三审三校 | 干什么 |
| --- | --- | --- |
| 编辑 / 记者 | 初审 + 一校 | 投素材、改稿、提交 |
| 部门主任 | 复审 + 二校 | 看标注、退回或通过 |
| 分管领导 | 终审 + 三校 | 看导向与全局、签发 |
| 台领导 / 管理员 | —— | 只看审计报表，不进流程 |

**角色必须可合并。** 小编辑部常常只有两个人，部门主任和分管领导是同一个人。
这是从「一人多岗」的实况推出来的硬需求，不是简化偷懒。系统要允许一个账号同时持有多个角色，
但**每一次审批仍然分别留痕**——合并的是人，不是责任。

> **2026-08-29 修订**：原先四个角色只有前三个在代码里存在，且是前端切换器直接自报，无鉴权。
> 现决定做账号 · 角色 · 权限（[requirements.md](requirements.md) 7.12–7.25，轨道 C），
> 采用**固定组合方案**——角色↔权限写死在代码里，**不做权限配置界面**。
>
> 「角色可合并」这条从设计约束变成了实现机制：**一个账号持有多个角色**，
> 顶栏切换器的语义从「切换是谁」变成「切换以什么身份行使」。
> 这同时解决了演示的一屏切换与真实鉴权之间的冲突——演示不变，机制变真。
>
> 「台领导 / 管理员」在代码里一直不存在，由 7.19 补上；它正是全流程监控看板（6.21）的使用者。
> 类型上必须与前三个分开（`WorkflowRole` ⊂ `SystemRole`），**否则状态机会给它算出审批按钮**。

## 三、稿件状态机

> **2026-08-28 修订**：原状态机漏了行业流程里的两个环节——「复核修改」与「征求意见/会签」，
> 且「三审三校」的**校**没有任何表达。下图目标态中的审核内核已由轨道 A 落地，
> 对应 [requirements.md](requirements.md) 5.9–5.13；三审界面 5.14 由轨道 B 继续完善。

```
草稿
 │
 ├─ 入口准入 ─┬─ 硬拦 ──→ 已拒绝（模型完全不碰，留痕）
 │            ├─ 要理由 ─→ 填选题依据 ─┐
 │            └─ 仅留痕 ───────────────┤
 │                                     ↓
 │                              AI 生成（走网关）
 │                                     ↓
 │                    ┌────→ 预检（自动标注，按校次分组）
 │                    │                ↓
 └────────────────────│───→ 待初审 ＋ 一校
                      │                ↓（通过）
                      │         待复审 ＋ 二校
                      │                ↓（通过）
                      │           待会签（可跳过）
                      │                ↓（会签完成）
                      │         待终审 ＋ 三校
                      │                ↓（签发）
                      │             已签发 ──→ 已发布
                      │
                      └── 复核修改 ←── 任一审级退回（带理由，进审计）
```

**校次不是状态。** 行业里「初审 + 一校」是同一个人同一步，所以校次是
**预检标注的分类**（哪一校该看哪一类问题）＋**审级的职责声明**，不新增状态。
状态机相对原版只多两个：`复核修改` 和 `待会签`。

### 状态说明

| 状态 | 谁能操作 | 可迁移到 | 校次职责 |
| --- | --- | --- | --- |
| `草稿` | 编辑 | 入口准入判定后 → `待初审` 或 `已拒绝` | —— |
| `已拒绝` | —— | 终态。留痕，可申诉（v2） | —— |
| `待初审` | 编辑 | `待复审` / 退回 `复核修改` | **一校**：错别字、语病、标点、格式 |
| `待复审` | 部门主任 | `待会签` 或直接 `待终审` / 退回 `复核修改` | **二校**：数据、人名、地名、术语、排版一致性 |
| `待会签` | 部门主任 | `待终审` / 退回 `复核修改` | —— 会签方填名字 + 意见，进审计 |
| `待终审` | 分管领导 | `已签发` / 退回 `复核修改` | **三校**：通读、排版效果、整体一致性 |
| `复核修改` | 编辑 | 重新预检 → 回 `待初审` | 改稿后**重跑预检并按轮次留痕** |
| `已签发` | 分管领导 | `已发布` | —— |
| `已发布` | —— | 终态 | —— |

**退回必须带理由，且理由进审计。** 这是责任链的一部分——不写理由退不回去。

**退回统一落 `复核修改`，不逐级回退。** 原设计「复审退回 → 待初审」看着更细，
实际上编辑还得再点一次才能改稿，**一次退回两步**；而且改完的稿子没重新预检，
新引入的错误没人发现。改成统一落 `复核修改`、改完重走预检与三审，
既少一次点击，留痕也更漂亮——**每一轮都能看出改了什么、又命中了什么**。

**会签是可选分支。** 不涉及其他部门的稿子，复审直接进终审；涉及的走 `待会签`。
这是事业单位的常态，也是原线性状态机装不下的那一条。

## 四、留痕规则：AI 参与度是管理指标，不只是合规记录

每一次流转都记录：**谁、什么时间、看到的是哪个版本、改了什么**。

在此之上做一件别人做不了的事：

> **AI 参与度在每次流转时重算。人改得越多，AI 占比越低。**

这个数字有两个用途：

1. **合规**——满足《人工智能生成合成内容标识办法》要求的可追溯，且比「打个标」精细得多。
2. **管理**——**如果一篇稿子以 AI 参与度 100% 一路签发，说明三审三校形同虚设，没人真看过。**

第二个用途是给台领导的抓手：**它能暴露走过场的审核。**
方正、大洋给不了这个数字，因为它们不知道哪句是 AI 写的。

### 句级来源标记

每一句话带一个来源标签：

| 标签 | 含义 |
| --- | --- |
| `ai` | AI 生成，原样保留 |
| `ai-edited` | AI 生成，人改过 |
| `human` | 人新写的 |
| `source` | 从原通稿原样引用的 |

AI 参与度 = (`ai` 句数 + `ai-edited` 句数 × 0.5) / 总句数。权重可调，demo 里说明口径即可。

**这是我们相对方正/黑马唯一的结构性优势**——它们拿到的是成品，我们在生产现场。

## 六、这一版不做

- 申诉流程（`已拒绝` 是终态）
- 多人并行编辑 / 版本合并
- 发布到真实平台（留按钮）
- 角色权限的管理界面（三个角色写死）
- 稿件检索与归档
